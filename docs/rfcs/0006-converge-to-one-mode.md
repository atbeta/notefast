# RFC 0006: 收敛到唯一模式 — 边界、前置条件与路线

- 状态：草案（待确认）
- 日期：2026-09-10
- 依赖：RFC 0001（vault 模式）、0002（身份与 ingest）、0003（写回与冲突）、0004（文件同步）、0005（vault-first 统一）
- 相关：`docs/plans/vault-mode.md`、`AGENTS.md`

## 摘要

vault 模式落地后，项目里同时存在两套词汇：**文件层的事实**（目录树、`.trash/`、冲突副本、未解析链接）与**索引层的视图**（所有文档、收集箱、归档、回收站、资源）。两套都合理，但**它们之间的关系从来没写下来过**，于是每一处交互都要临场判断，用起来像「收不住了」。

本 RFC 只做一件事：把边界写成硬规则，并说明「收敛到唯一模式」需要先满足什么。**它不引入新功能**；它约束后续所有功能。

## 问题

真实出现过的困惑（都来自使用，不是假想）：

| 困惑 | 根因 |
|---|---|
| 收集箱到底进不进目录？ | 「位置」与「状态」谁权威没定 |
| 根目录里哪些是采集件、哪些是手写的？ | 状态只活在索引里，界面不显示 |
| 在 `notes/books` 里点新建，文件跑到根目录 | 创建路径没有「当前位置」概念 |
| 左侧目录要等扫描才出现 | 视图不订阅变更（其实是树不刷新） |
| 归档在文件里看不到，编辑正文还可能被拉回 note | 文件表达不了 `archived` |
| db 模式的「回收站」和 vault 的 `.trash/` 是两回事 | 同一动作两套语义，入口并排 |

## 硬规则

### R1 位置归用户，状态归 frontmatter

- **文件放哪儿完全由用户决定**：应用不因为状态变化移动用户的文件，也不因为文件位置变化改状态
- **状态只有三个值**：`note`（普通）、`inbox`（收集箱）、`archived`（归档），载体是文件 frontmatter 的 `notefast_status`（RFC 0005 U-11 已让三个值都能表达）
- 推论：
  - **收集箱不映射目录**。「`Inbox/` 目录 = 收集箱」被明确否决：那会逼应用搬用户文件，且 `Inbox/2026/`、`Notes/Inbox/` 这类嵌套无法自洽
  - 归档、取消归档都可以在文件里手写完成，不需要经过应用
  - 视图（收集箱 / 归档 / 标签 / 智能视图）都是**查询**，不是位置

### R2 应用只决定自己新建文件的位置，绝不移动用户已有的文件

- 新建时的落点优先级：显式 `dir`（用户当前所在的目录）> 采集默认目录（仅收集箱）> vault 根
- 采集默认目录是**默认落点**，不是状态绑定（`data/vault-capture.json`，留空 = 根目录）
- 已存在的文档，位置永远来自 `vault_files.rel_path`——改配置、改标题、改状态都不会搬家
- 唯一例外：用户显式执行的重命名/移动操作（应用内改名 → 同目录改名）

### R3 一切写入都必须落盘

- vault notebook 里**不允许存在只活在索引中的文档**。AI 采集、API 写入、MCP 创建、导入——每个写路径都负责把文件写到磁盘（写回是其实现，不是可选项）
- 推论：
  - `VAULT_WRITEBACK=false` 只作为排障开关存在，不是受支持的运行模式（文档里要写明）
  - 任何新写路径合入前必须回答：**它写哪个文件？** 答不上来就不该存在
- 这条是「统一」的关键：它消灭了「索引态草稿」这个第二权威

### R4 界面必须区分「文件层事实」与「索引层视图」

- 文件层：目录树、`.trash/`（回收站目录）、冲突副本、未解析链接、附件
- 索引层：收集箱、归档、标签、智能视图、实体/图谱
- 同一个概念只允许一个入口：vault 模式下**回收站**指向 `.trash/`（已在 U-9 落地），不再并列 db 模式的软删除视图
- 状态必须在文件列表里可见（已在 U-11 落地：树上的收集箱/归档标记），否则 R1 对用户不可见

## 明确不做

- 收集箱/归档映射到目录；目录即分类
- 附件目录树、按类型自动分目录
- 应用自动整理用户目录（移动、归档、按规则归位）
- 「索引态草稿区」（与 R3 直接冲突）
- 在 vault 里保留 db 模式那套软删除回收站（两套删除语义并列）

## 收敛到唯一模式的路线与前置条件

**目标状态**：vault 是唯一模式，「指向一个文件夹」是唯一入口；db 模式降级为 legacy（保留可用、只修 bug），最终删除。

| 阶段 | 内容 | 状态 |
|---|---|---|
| P0 | 规则落地：R1（状态三值进文件）、R2（新建落当前目录 + 采集默认目录）、R4（状态可见、回收站指向 `.trash/`） | **完成** |
| P1 | **性能**：10k 文件对账从 185s 降到 < 60s（批量 ingest 改造，见 `docs/plans/vault-mode.md` U-7 的三步） | 未完成 |
| P2 | **parity**：U-5 修订历史（索引侧快照 + 写回恢复）、U-6 分享身份改 `rel_path` | 未完成 |
| P3 | **迁移**：db → vault 的一次性投影（导出带 `notefast_id` frontmatter，ingest 认领 doc id，保住分享与引用）；旧库留作只读归档 | 未开始 |
| P4 | 新安装默认 vault；db 模式冻结（文档标注 legacy，不再加功能） | 部分（README 已以 vault 为首选） |
| P5 | 在 1.0 边界评估删除 db 模式代码 | 未开始 |

**P1 是硬门槛**：db 模式建 10k 文档是秒级，vault 现在要几分钟——不修完就统一，等于让所有大库用户升级即变慢。

## 开放问题

- 采集默认目录要不要给「新安装默认 `Inbox/`」而不是留空？倾向留空（不替用户决定），但在设置里给出建议值
- 冲突副本要不要提供「一键采纳 NoteFast 版本」？（当前只列出，让用户自己比对）
- `notes/`、`attachments/` 这类约定目录要不要在首次导入时建议？（Obsidian 用户预期不同，暂不做）
